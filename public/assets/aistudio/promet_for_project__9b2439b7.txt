# FULL PROJECT SPECIFICATION — EVENT INVITATION & QR CHECK-IN MANAGEMENT SYSTEM

## 1. PROJECT OVERVIEW

Build a complete, professional, secure, responsive web application called "Event Management System".

The application will manage event invitations, guest lists, unique QR codes, employee check-in operations, attendance tracking, and administrative reports.

The system must be suitable for real company events, with multiple employees scanning invitations from different devices simultaneously.

The application must be built using ONLY:

- HTML5
- CSS3
- Vanilla JavaScript (ES6+)
- Firebase Authentication
- Cloud Firestore
- Firebase Cloud Functions or another appropriate trusted server-side mechanism when required for secure operations
- GitHub Repository
- GitHub Pages for website hosting

Do not use React, Vue, Angular, TypeScript, Next.js, or other frontend frameworks.

Do not require a paid service for the initial deployment if a suitable free-tier implementation is possible. Verify current free-tier limitations before choosing Firebase services.

Explain any feature that requires a paid plan or cannot operate securely within the selected free-tier configuration.

The project must be organized, maintainable, documented, secure, and easy for a beginner to understand and modify.

IMPORTANT: Do not generate a superficial demo. Build a complete application with real Firebase integration, functional forms, real database operations, authentication, role-based authorization, QR scanning, and check-in validation.

Do not use fake statistics, mock guests, hardcoded demonstration users, or localStorage as a substitute for the database.

## 2. SYSTEM ARCHITECTURE

The system consists of four main components:

1. Frontend website hosted on GitHub Pages.
2. Firebase Authentication for user sign-in.
3. Cloud Firestore for guests, events, invitations, and attendance records.
4. A trusted backend mechanism for sensitive operations, such as invitation validation, one-time check-in, account provisioning, and privileged administrative actions.

The main workflow is:

GitHub Pages Website
→ Login Page
→ Firebase Authentication
→ Verify User Role
→ Admin Dashboard OR Employee Check-in Page

Admin operations and employee check-in operations must use the same Firestore database.

All devices must receive consistent, current data.

Use an appropriate Firestore listener for live attendance statistics and guest status updates.

Never trust a role, invitation status, or check-in result supplied only by frontend JavaScript.

All security-sensitive operations must be validated by trusted server-side code or another Firebase mechanism with equivalent security guarantees.

Do not expose Firebase Admin SDK credentials, service account keys, private API keys, or other server secrets in frontend files or the GitHub repository.

Firebase client configuration may be present in the frontend when appropriate, but it must be protected by Authentication, Firestore Security Rules, and applicable platform restrictions.

Cloud Firestore:

https://firebase.google.com/docs/firestore/security/get-started

## 8. QR CODE GENERATION

Generate a unique QR invitation for every guest.

The QR code must contain an opaque, unpredictable invitation token or a secure invitation reference.

Do not encode passwords, private guest information, or authorization claims directly in the QR code.

The token must not be a sequential guest ID or an easily guessed value.

Use cryptographically secure randomness generated in a trusted environment.

Store only an appropriately protected token representation when practical.

The backend must be able to validate the presented token securely.

Every token must be associated with one guest and one event.

Required features:

- Generate QR codes for individual guests.
- Generate QR codes for imported guests.
- Download an individual QR code.
- Generate downloadable invitation images.
- Generate a printable PDF containing multiple invitations if practical.
- Include guest name, company, event name, and invitation QR on the invitation design.
- Allow reissuing an invitation.
- Revoke the previous token when a replacement is issued.
- Display the invitation status.

QR codes must not be accepted merely because their contents resemble a valid guest ID.

The backend must verify token validity and invitation status.

Use a maintained QR-generation library and document its source.

Use a camera-compatible QR-scanning library, such as a maintained version of html5-qrcode or another appropriate alternative.

Official reference:
https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia

Camera access normally requires HTTPS or localhost.

Ensure the deployed GitHub Pages website uses HTTPS.

Handle camera permission denial, unsupported browsers, unavailable cameras, and unreadable QR codes.

Provide a clear fallback message when scanning is unavailable.

## 10. EMPLOYEE CHECK-IN INTERFACE

Create a dedicated employee page.

The interface must be extremely simple because employees will use it while managing a queue at an event entrance.

Suggested layout:

EVENT CHECK-IN

[Open Camera]

[QR Scanner Area]

Result panel:

- Guest name.
- Company.
- Event name.
- Invitation status.
- Check-in time.
- Clear result message.

Use large controls and readable text.

### Successful Scan

When an eligible invitation is scanned:

- Validate the token using a trusted backend.
- Verify that the event is active.
- Verify that the invitation belongs to the selected event.
- Verify that the invitation is not cancelled or revoked.
- Verify that the invitation has not already been used.
- Record the check-in exactly once.
- Return the authorized guest details.
- Display a green success indicator.
- Show a clear message such as "ENTRY APPROVED".
- Play an optional short success sound.
- Prepare the scanner for the next guest.

### Invalid Invitation

If the token is unknown or invalid:

- Do not permit entry.
- Record the rejected attempt where appropriate.
- Display a red indicator.
- Show "INVALID INVITATION".

### Previously Used Invitation

If the invitation has already been used:

- Do not create another successful check-in.
- Display an amber or red warning.
- Show "ALREADY CHECKED IN".
- Display the original check-in time when authorized.
- Record the duplicate attempt.

### Cancelled or Revoked Invitation

Reject the invitation and display a clear reason.

### Network or Server Error

Never display a success message when the server has not confirmed the check-in.

Show a clear network or verification error.

Do not silently permit entry when verification fails.

Provide an explicit retry option.

### Camera Handling

Request camera permission only after the employee clicks the scan button.

Stop camera streams when scanning is stopped or the user leaves the page.

Avoid accidentally processing the same QR repeatedly.

Provide a manual search fallback if enabled by the administrator.

Do not expose the complete guest database to employee browsers just to make scanning work.

## 11. ATOMIC CHECK-IN AND DUPLICATE PREVENTION

This is one of the most important security requirements.

Multiple employees may scan the same QR code at approximately the same time.

The system must guarantee that only one successful check-in is recorded for a single-use invitation.

Implement a trusted server-side check-in operation.

The operation must:

1. Authenticate the employee.
2. Verify the employee's role and event access.
3. Validate the invitation token.
4. Check the event status.
5. Check the invitation status.
6. Atomically verify and claim the invitation.
7. Create the successful check-in record.
8. Record the employee identity and server timestamp.
9. Return a structured result.

Use an appropriate Firestore transaction or another mechanism that provides equivalent atomicity.

Do not implement duplicate prevention using only frontend checks, localStorage, disabled buttons, or ordinary non-transactional updates.

Do not allow an employee to mark an invitation as checked in by writing directly to an unrestricted Firestore document.

If a retry occurs after a network timeout, design the operation so that it does not accidentally create a second successful check-in.

Use server-generated timestamps.

The check-in operation must return distinct result codes, such as:

- SUCCESS.
- INVALID_TOKEN.
- ALREADY_CHECKED_IN.
- CANCELLED_INVITATION.
- EVENT_NOT_ACTIVE.
- UNAUTHORIZED.
- TEMPORARY_ERROR.

Document how each result is handled by the frontend.

## 14. FIRESTORE SECURITY RULES

Create a production-conscious firestore.rules file.

Apply the principle of least privilege.

Requirements:

- Deny unauthenticated access to private guest and attendance data.
- Do not trust roles supplied by client requests.
- Restrict employee access to authorized event data.
- Prevent employees from changing invitation status directly.
- Prevent employees from editing guest records.
- Prevent ordinary users from changing their own role to ADMIN.
- Prevent direct client writes that bypass secure check-in validation.
- Protect invitation token records.
- Restrict administrative operations to authorized administrators.
- Protect audit log integrity.
- Validate allowed fields and data types for client-accessible writes.
- Deny unspecified access by default.

Privileged backend operations must perform their own authorization checks because server-side Admin SDK operations bypass Firestore Security Rules.

Do not assume Firestore Security Rules automatically protect trusted server code.

Include tests using the Firebase Emulator Suite or another supported testing approach.

Test both authorized and unauthorized scenarios.

Never deploy permissive development rules such as unrestricted read/write access.

Official reference:
https://firebase.google.com/docs/firestore/security/rules-conditions

First, explain the architecture and identify the services that are actually required.

Then provide the exact project folder structure.

Next, explain the Firebase project setup and the distinction between frontend hosting and backend execution.

Identify any feature that requires additional configuration or billing before implementation.

Do not start with a fake dashboard or a mock QR scanner.

Do not ask me to repeat requirements already stated in this specification.

Proceed step by step, clearly explaining what each component does and how I can test it before moving to the next phase.
